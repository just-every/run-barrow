# Connection and document security

Pier credentials stay in the server-only secret bindings declared in deploy.json. Hosted custody uses the platform’s encrypted secret store; local .dev.vars and source session files are private owner-only files. Use a Pier stock operator, the least available role for order reservation, rather than owner access where possible. Pier has no dedicated narrowly scoped Barrow service token today.

To replace an expiring or compromised connection, obtain a new authorized session in Pier, stop this Barrow process, and run the existing connection helper with --origin and --session-file. The helper validates the current Pier role without printing the cookie, then replaces .dev.vars atomically at mode 0600. Restart Barrow, read its stock catalog and check its commercial audit. The first authorized connection check or provider call observes a changed deployed binding as pier.connection-configured, pier.connection-rotated or pier.connection-revoked. These are system observations of deployment changes, not assertions about who operated the deployment. Values and keyed fingerprints never enter the audit, diagnostics or archive. Revoke the replaced session at Pier; changing Barrow’s binding cannot revoke someone else’s sign-in. For hosted installs, replace/remove the declared PIER_SESSION platform secret through the existing deploy lifecycle; never put a credential in a command argument, source file or issue.

All seed API routes, including application forms, signed mail callbacks, transfers and unknown paths, admit at most 600 requests per fixed minute per trusted platform IP. Missing IPs share one bucket. Only a per-installation HMAC digest and expiry/count are stored; rate rows are excluded from archives and expired windows are removed on requests. A refusal is 429 with Retry-After. Existing stricter authentication and application-intake limits still apply. Rate admission never substitutes for identity, origin, signature, current role or file authorization.

PO, quote and application intake all use the same size/type and active-content checks before storage. Recognized PDF actions, embedded files, encrypted/object-stream content, HTML/SVG, archive and executable payloads are refused. Downloads remain private, attachment-only, no-store, sandboxed and nosniff. These conservative byte checks do not establish that a document is free of malware. Files remain labelled not malware-screened; no file is submitted to another service. DATA-004 remains partial pending an approved private scanner and custody policy. Existing stored files have no new clean verdict.
