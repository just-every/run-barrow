# WizCommerce move-in

WizCommerce documents [Excel order and quote exports](https://knowledge.wizcommerce.com/import-export-orders-and-quotes) with three alternative views: document headers, item rows and combined master rows. Its [FTP exports](https://knowledge.wizcommerce.com/ftp-integration) supply separate header and item files keyed by UUID, plus customer files. Download those files through the merchant's existing secure transfer; Barrow does not connect to an FTP server in this importer.

The existing signed-in owner uses `POST /api/barrow/imports/wizcommerce/preview`, then resends the unchanged JSON with the exact returned `fingerprint` and an owner `reason` to `POST /api/barrow/imports/wizcommerce/apply`. `GET /api/barrow/imports/wizcommerce` reads retained imports and labeled history. These doors preserve the same owner-only scope and transaction guards as the SparkLayer importer in `docs/SPARKLAYER.md`.

The JSON contains `tenant`, `authority` and `scope` as documented there, plus exactly one of:

- `ftp`: `headers` and `items`, each with `name` and UTF-8 `csv`; optional `customers`, `contacts` and `addresses` have the same shape.
- `workbook`: a plain XLSX `name`, canonical `base64` bytes of at most 1 MiB and `layout`, either `split` or `master`. The split layout reads the documented document and item sheets. The master layout reads their combined sheet. Formula cells, external references, macros and unsafe workbook packages are refused by Barrow's existing workbook inspector.

Optional `entityWorkbooks` contains at most three separate XLSX files with `name` and `base64`, holding Customers, Contacts, Addresses or Website Users sheets. The main workbook may hold those sheets too; do not repeat an entity ID. Optional `websiteUsers` is a separate CSV file with `name` and `csv`. Preview and apply create no login authority and send no mail. Website-user candidates are listed for a separate explicit review.

In the installed app, open **Move in**, upload a JSON manifest under **WizCommerce move-in**, then preview the source. Review native counts, currency totals, quantities, missing entities and rejected fields. Enter an approval reason and confirm the fingerprint before applying. A source edit clears the review. Accounts shows the resulting native customer, contact, bill-to and ship-to records.

Customer columns are Customer ID, Name and Email. Map each source customer to a stable native ID in `authority.customers`. An existing account keeps its native profile. To create a new one, include its complete current account value under `nativeAccounts[accountId]`: name, lowercase email, Pier customer ID, terms days, minimum cents and current prices, using the account fields in `docs/MOVE-IN.md`. Its name and email must match the source customer. Historical line prices never become current account prices. Duplicate company identity or email requires resolving the mapping against the native directory before apply. No imported account bootstraps purchasing access from a matching sign-in email.

Contacts use Contact ID, Customer ID, Name, Email, Phone and Role. Addresses use Address ID, Customer ID, Kind (bill-to or ship-to), Name, Line 1, Line 2, City, State, ZIP and optional Delivery Instructions. The existing native US address validator checks format and state ZIP range; this is not carrier verification. The first address of a kind becomes default only when that account has none. `entityColumns` can map each logical field in `customers`, `contacts` or `addresses` to another supplied header; defaults use id, name and email for customers, and id, customerId and the corresponding camel-case location fields for contacts and addresses. Unknown source fields are named in rejected fields and retained only in the original, never silently activated. A customer absent from the supplied entity set is named as missing; a mapping alone can only use an existing native account.

Default logical columns are `id` → Document System ID, `reference` → Document ID, `customerId` → Customer ID, `type` → Type, `currency` → Currency, `total` → Total Order Value, `productId` → Product ID, `quantity` → Quantity and `unitPrice` → Unit Price. Optional fields use Shipping, Status, Tracking, Date, Case Pack, Increment, Unit, Payment Status and Paid Amount. When a merchant's export uses other names, supply a `columns` object mapping these logical fields onto actual header names. No universal spelling is assumed.

UUID joins are authoritative. A line may join by its unique visible reference when no UUID is supplied; if both appear they must agree. Duplicate UUID headers, ambiguous references, orphan lines, mismatched customers and missing customer export coverage refuse the batch. Master rows for one document must repeat the same header facts. Orders and quotes remain distinct labeled history, preserving source status, paid amount and payment status, reference, unit, exact cents, source rows and workbook bytes. No amount is treated as a native receipt or accounting authority.

The preview reports source against planned counts, quantities and financial totals by currency and status, plus source against planned native customer, contact and address counts, newly created counts, website-user counts and every unsupported native step. Applying requires the exact reviewed source and native snapshots. Replays across FTP, split workbooks and master workbooks add no second history document; changed financial facts refuse instead of rewriting history. Source entity IDs and customer mappings remain stable across formats. Native location edits survive replay; changed imported location facts require a distinct reviewed source ID. Retired tenant source custody refuses reactivation. Source case packs and increments map to the account's existing SKU rules while source prices remain historical. Source lists are not supplied by these formats.

DATA-001 owner exports contain the source originals and history; customer exports contain neither. Archives retain native customer and location records and inert history; restore sends no invitation. Existing account erasure retires shared originals and mapped account history atomically. Copies downloaded earlier and originals held by WizCommerce remain separate custody.

After history import, review each `invitationCandidates` entry and explicitly request `POST /api/barrow/imports/wizcommerce/invite` with the returned `importId` (the apply result's `id`), import `fingerprint`, exact candidate `email`, `confirm: true`, a review `reason` and an explicit ACC-002 `policy` (rights, permitted locations and both purchasing limits). This separate action uses the existing native invitation flow, including collision review, seven-day exact-email acceptance and delivery states. It requests one pending invitation per source tenant, account and email. Replays send no second invitation. Native sign-in alone still grants no company access before explicit invitation acceptance. Source custody retirement refuses later invitation requests; restored history never sends invitations automatically.
