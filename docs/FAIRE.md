# Faire order intake

The signed-in installation owner operates the read boundary at `/api/barrow/faire`.
Configure `FAIRE_CONNECTIONS` through the installation's server secret storage. It is a JSON object keyed by the merchant's stable brand identifier. Each connection names `origin` and `accessToken`; an OAuth connection also supplies `appCredentials`, the application's encoded credentials. Obtain brand authorization with read-only order scope through Faire before provisioning these values. Multi-brand integrations require one separately authorized OAuth token and application credentials per brand; duplicate connection aliases are refused. Barrow does not register an application or exchange an authorization code on a brand's behalf.

The production origin is `https://www.faire.com`; the supported sandbox origin is `https://www.staging.faire.dev`. A controlled HTTP boundary on the loopback address is permitted only in local development. The caller cannot supply an arbitrary destination. Reads send the brand token using `X-FAIRE-ACCESS-TOKEN`, or the OAuth token and application credentials using `X-FAIRE-OAUTH-ACCESS-TOKEN` and `X-FAIRE-APP-CREDENTIALS`. Redirects are refused. See the [Faire developer documentation](https://developers.faire.com/) for account provisioning and authorization.

Use same-origin authenticated POST requests to these public doors:

- `/api/barrow/faire/configure`: `brand`, explicit boolean `enabled`, and `reason` record owner authorization or withdrawal.
- `/api/barrow/faire/poll`: `brand` reads one page from the saved cursor. `restart: true` starts another complete poll, preserving source identities and reviewed history. A failed read or invalid page advances nothing. A successful page atomically stores the orders and its next cursor. Poll until `complete` is 1; no webhook is assumed.
- `/api/barrow/faire/match`: `brand`, original Faire order `id`, exact reviewed `revision`, existing `accountId`, an explicit `skuMap`, and `reason` approve the retailer and each line match. Unknown SKUs remain in review. The account must be active, hold every mapped SKU, and use the source currency. Source prices remain unchanged by current account prices. A repeated approval returns the same order; a changed source revision returns to review. An already ingested order cannot move to another customer.

The page contains `orders` and a nullable next `cursor`. Each order has an `id`, `retailer_id`, `state` and `items`. Items carry their original `id`, `sku` (or product variant ID), positive integer `quantity`, currency, and an integer minor-unit price. The controlled boundary accepts `price: {currency, amount_minor}`; the cent-denominated representation uses `price_cents` with item or order `currency`. Optional `payout_costs` retains reported commission basis points, commission flat fee and payout fee. Missing fees stay unknown. Order and line identities are unique within the brand, never inferred from customer names or purchase-order references.

Intake retains only the whitelisted commercial facts, opaque retailer identifier and reviewed native account and SKU matches. It does not retain source addresses, contacts or arbitrary source bodies. Original Faire order IDs remain visible once in the private intake list and the owner export, with the full reviewed source revision. Faire owns settlement: intake never creates a Barrow checkout, card payment, invoice, stock reservation or outbound message. The separate native order ledger continues to represent native orders.

Fulfillment and backorder reporting includes the exact ordered quantities and source IDs from ingested Faire lines, filtered by account. Shipped quantity, warehouse and delivery remain explicitly unknown because this read boundary does not provide confirmed quantities or warehouse attribution. These unknowns never enter Pier's fill denominator. A changed source is visibly pending owner review. Supplier functional-role access to these new source rows remains denied until exact source scope can be confirmed.

Every configuration, reconciled page and matching decision joins the append-only staff audit with actor, source, time, revision and reason. Buyers and agents cannot operate intake or read its staff decisions. Owner JSON and per-kind CSV exports include `faireorders`; owner archives preserve the source and reviewed records but restore synchronization disabled. Credentials never enter these records or archives. Accounts with matched Faire orders cannot use unused-account erasure. Faire retains its own provider records and must handle provider-side revocation or erasure separately.
