# Company agents in Barrow

The installation has one shared agent door at `/mcp`, with discovery, OAuth resource metadata, signed company policy at `/api/rer/agent-policy`, and a person's review and Pause controls at `/agents`. It supports MCP 2026-07-28 and 2025-11-25. The copied runtime and published CLI are pinned to Base `940aba7afd04052fdb11f4c878e70781d7abda50` (runtime refresh after `rer-v0.2.91`; CLI remains 0.2.91).

The wholesale account operator can read an authorized account, its live catalogue, shared shopping lists and orders, validate a cart, download an order-form result and prepare a current-price draft or a structured substitution proposal under an existing owner-authorized account grant. It uses the same account, catalogue, cart and order services as the portal. Draft preparation changes reversible internal work and is classified `standard` from its actual line count; it neither reserves stock nor charges, submits, approves or contacts anyone. Its exact account, item quantities, native revision and agent/preparer identity accompany review and audit. Imported or customer text is untrusted and cannot choose policy or confer authority.

The seed-owned runtime registry is `src/barrow/agent-door/registry.ts`; `agent-surface.json` supplies its conformance fixtures. The generated [company agent guide](AGENTS.md), published at `/docs/agents`, lists the thirteen native tools with their exact schemas, scopes, classes, computed measures and fixtures. Regenerate it with `node scripts/agent-docs.mjs write` and check it with `node scripts/agent-docs.mjs check`. The copied runtime adds required idempotency keys and revision inputs before those schemas are documented. `barrow.prepare-order` and `barrow.prepare-substitution` are preparation-only specialist prompts. They return deterministic instructions, ignore arguments and load no account data; current tools remain the only authorized source of commercial facts.

The descriptor and runtime declare tools, policy, Pause, audit, idempotency and prompts. Resources, events and subscriptions remain undeclared capability families and retain typed `capability_not_declared` refusals; their catalogues are empty. Tools return no public resource links. Read the actual prepared draft or proposal with its corresponding read tool. Private lists remain unavailable to agents.

Record tools resolve an audit-safe native target through current Barrow authorization. Account and catalog reads, shared-list collections, cart previews, order forms and proposal-grant collections name the authorized account. Individual order, shared-list and proposal reads name that native record. Draft preparation retains its account target; proposal preparation retains its original order target. Workspace and account-directory calls have no single record target and retain `null`. The copied runtime stores the resolved pair in audit `resource` and applicable review and approval `summary.nativeTarget`, checks it again before approval execution, and preserves authorized attribution for blocked, unset and paused calls. Missing, foreign, private, revoked and erased records confer no identity. Targets never grant commercial authority. The descriptor journey and `tests/agent-door/audit-targets.mjs` compare these identities with native session reads and inspect policy variants through public HTTP.

`barrow.cart.form` requires `accountId` and a `layout` of `vertical` or `matrix`. Its optional `cart` accepts at most 100 native cart lines with `sku` and `quantity`, plus optional `unit` and `buyerSku`; omitted or empty carts retain the blank-form behavior. It returns the required strings `filename`, ISO `currency` and `csv`. Populated vertical forms retain quantities and include selected selling units; matrix forms accept base units only and return native `UNIT` for selling-unit lines. Current account prices, sponsor and account admission, `catalog:read`, standard classification and read-only annotations are unchanged. The tool passes admitted arguments to the same `cartCommand` as the portal, grants no buying-profile authority and adds no submission, stock, payment or outreach capability.

Its helper `tests/agent-door/cart-form-parity.mjs` compares populated, omitted and empty forms through native HTTP and MCP; the same helper runs from `tests/agent-door/native-journey.mjs` during autonomous and held conformance, including quantity-preserving uploads of downloaded forms, malformed-cart refusal and selected selling-unit prices with the native matrix refusal. The built-page journey opens actual downloads at desktop width and optionally captures the same forms at phone width, comparing their filenames, currency and exact CSV bytes with MCP. Business `owner_id` and team `id` bind to native operator ids through signed Business settings. An email is never a token-to-account lookup. Unknown, inactive, excluded or natively inadmissible sponsors are refused. Native bearer sponsorship is currently owner/admin only; a team member does not acquire commercial or policy administration from the roster. A Business owner is a policy owner, a Business team admin a policy editor, and a member has no policy role. Promoting somebody locally does not make them a Business editor. The native operator is reread for each call and again before an atomic mutation. Existing local seven-day draft credentials retain their scope; an account-scoped proposal credential retains its existing catalogue/order reads and structured proposal submission on MCP. A company agent must name an active native proposal grant authorized by its own sponsor; a grant id never substitutes for current native authorization. Manager/buyer decisions and proposal execution remain with people. Integration, import and provider credentials keep their existing purposes.

A person still submits and approves orders and decides native proposal, purchasing and finance approvals. The door cannot turn an agent's confirmation flag into that person's act. Device caches/scanners, connector transports, reviewed imports and installation commands stay in their own declared doors. Company tools for outreach, stock execution, refunds, role/grant changes, commercial acceptance, cutover activation and the wider proposed ct surface are not implemented by this adoption. No paid model, mail, payment or stock mutation is reachable from the declared tools. Pier is the only outbound read provider; a disconnected or refused Pier stays unavailable, without invented inventory.

Legacy bearer HTTP is a compatibility transport into that same MCP handler. Its catalogue, account, order and shared-list reads and cart/draft/proposal commands have no direct native-service dispatcher. Compatibility calls use the shared runtime's modern MCP protocol internally, including URL elicitation. Under an explicit approval rule for `standard`, a pending HTTP call returns 403 with `code: approval_required`, `resultType: input_required`, `approval` (id, URL and expiry), `inputRequests`, `decision` and opaque `requestState`. It returns no commercial result and performs no commercial action. The named person signs in at that URL and approves the saved policy revision and summary; an agent confirmation cannot replace that decision. Rejection returns `approval_rejected`. An explicit blocked rule returns `policy_blocked` with the actual class, rule and revision.

To recover an approved GET, repeat the original route and query arguments with the returned `requestState` query parameter. For a command, keep the original payload and idempotency key, and pass `requestState` beside `type` and `payload` in the request body. Continuation state is transport metadata, never a tool argument. The shared policy pipeline binds recovery to the current authenticated person and agent, original tool and exact arguments; another credential, changed input, rejection, changed policy, Pause or revocation grants no old authority. The currently authorized read is checked again before returning content. Successful response bodies keep their ordinary shapes: the native object for a read, and an object containing `result` for a command. The JSON response headers `x-rer-agent-decision` and, after approval, `x-rer-agent-receipt` carry policy and approval evidence without changing those bodies. Responses remain private and uncached.
